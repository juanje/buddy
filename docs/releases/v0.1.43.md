## Next action per project, WIP by area

The next-action marker (`>>`) now works per project instead of per area. If you have three projects in `@work`, each can have its own next action — they no longer fight for a single slot. WIP tracking moved from counting `>>` markers globally to reading what you actually have in your AGENTS.md Right now section, counted per area.

**What you could see**

- **Setting a next action in one project cleared the next action in another.** Both `#alpha` and `#beta` are in `@work`, but `set_next` on an alpha task wiped beta's `>>`. Now clearing only happens within the same project scope — or among untagged tasks in the same area.
- **Adding a task to a project with no next action did not auto-mark it.** The auto-mark check counted all open items in the area, not the project. A project with zero items but sharing an area with other tasks was treated as non-empty. Now the check is scoped to the project (or to loose tasks when untagged).
- **Completing a project's next action reported the wrong remaining count.** "3 open tasks remain" included tasks from every project in the area. Now the count and the hint text reference the specific project (`#alpha`) or loose scope (`@work (loose tasks)`).
- **The default WIP limit was 5.** With per-area semantics the right threshold is lower — it is now 3. You can still override it with `config(wipLimit)`.

**What changed underneath**

Daily consolidation no longer calls `tasks(only_next)` to check WIP. Instead, the consolidation prompt header includes a pre-computed "Active fronts per area" block parsed from AGENTS.md's Right now section. Each bullet tagged `@area` contributes one front to that area's count; untagged bullets go to "(general)". The consolidation LLM reads this block and writes a deferred item when any area exceeds the WIP limit — no task-tool call needed for the check.
